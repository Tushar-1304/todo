7. MESSAGE DELIVERY RULES
==================================================

Use these status meanings:

Sending:
The message currently exists only in the sender's browser and is waiting for a server acknowledgement.

Sent:
The server validated and stored the message successfully in PostgreSQL.

Delivered:
At least one active socket belonging to the other participant received and acknowledged the message.

Read:
The other participant opened the chat and advanced their read marker beyond or to that message.

Failed:
The server rejected the message or did not acknowledge it within a reasonable timeout.

The database is the source of truth.

Always save a message in PostgreSQL before broadcasting it to the recipient.

Every outgoing message must include a client-generated UUID called clientMessageId.

Create a database uniqueness constraint using:

sender_id + client_message_id

If a message is retried after a connection interruption, the server must not create a duplicate record.

If the same clientMessageId is received again from the same sender, return the previously created message.

Do not trust a sender ID provided by the browser.

Derive the sender identity from the verified server session.

13. SESSION AUTHENTICATION
==================================================

Do not use a public username/password system.

Do not use JWT unless there is a strong technical reason. Prefer secure opaque server-managed sessions because there are only two participants and sessions must be easy to revoke.

Access-code verification flow:

1. Browser submits selected identity and private access code over HTTPS.
2. Server validates the request.
3. Server applies strict rate limiting.
4. Server selects the correct access-code hash from environment variables.
5. Server verifies the access code using Argon2id.
6. Server generates a cryptographically strong random session token.
7. Server stores only a SHA-256 or similarly secure hash of the token in PostgreSQL.
8. Server sends the raw token in a secure HTTP-only cookie.
9. Server returns only safe participant information.
10. Browser redirects to /chat.

Session validation flow:

1. Read the HTTP-only cookie.
2. Hash the received token.
3. Look up an active, non-expired, non-revoked session.
4. Load the corresponding participant.
5. Optionally update last_used_at without causing excessive database writes.
6. Attach the participant to the Express request or Socket.IO socket.

Session expiration:

Use a reasonable configurable duration, such as 30 days.

Set it through an environment variable.

Support logout from the current device.

Optionally provide a secure way to revoke all sessions for both users through a maintenance script, not through a public admin page.

14. SOCKET.IO AUTHENTICATION
==================================================

The Socket.IO connection must be authenticated.

Because the application uses a same-origin HTTP-only session cookie, authenticate the socket handshake using that cookie.

Do not ask frontend JavaScript to read the HTTP-only cookie.

During the Socket.IO handshake:

1. Parse the session cookie.
2. Hash the session token.
3. Find an active session in PostgreSQL.
4. Load the participant.
5. Attach the participant to socket.data.
6. Reject unauthenticated sockets.

Join each authenticated socket to a participant-specific room:

participant:<participantId>

Suggested Socket.IO client-to-server events:

- message:send
- message:delivered
- messages:read
- chat:sync

Suggested server-to-client events:

- message:new
- message:confirmed
- message:delivered
- messages:read
- presence:changed
- session:invalid
- chat:error

Use acknowledgements for message sending.

Validate every Socket.IO payload on the server using Zod or equivalent validation.

Never trust browser data merely because it arrived over an authenticated socket.
